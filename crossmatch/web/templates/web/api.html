Recent crossmatches

GET /api/recent-crossmatches

Returns recent crossmatches for objects that had an alert in a time window, grouped by object, at a caller-selected detail level. Matches-only: an object with no catalog match is not listed.

Results are keyset (cursor) paged, newest first. Follow the top-level next_cursor to page through the whole window; it is null when the window is exhausted. The first page sets as_of and its cursors carry it, so one walk lists only alerts ingested at or before that time. The pin fixes which alerts are in the set, not their crossmatch state: an alert that gains its first match while you page can appear on a later page. A walk never repeats an object.

This endpoint does not filter or count: a filter parameter or response returns a 400 unsupported_parameter error; other unknown parameters are ignored. It runs within the {{ api.limits.request_budget_seconds }} s request budget, so a large page at detail=full can return a 400 query_too_expensive; request a smaller page_size if it does.

Query parameters

All parameters are optional
Parameter Values Description
start ISO-8601 timestamp (UTC) Window start. Defaults to end minus {{ api.recent.default_window_hours }} hours. The window may span at most {{ api.recent.max_window_hours }} hours.
end ISO-8601 timestamp (UTC) Window end. Defaults to now.
time_field ingest_time (default), event_time Which alert timestamp the window filters on: arrival time or observation time.
detail ids, position, matches (default), full Cumulative detail level per object (see below).
page_size positive integer Objects per page (default {{ api.recent.default_page_size }}), clamped down to the server maximum of {{ api.recent.max_page_size }}.
cursor opaque token A next_cursor from a prior page. It pins start, end, time_field, and detail; supplying any of those with a conflicting value is a 400.

Detail levels

Detail levels are cumulative, each adding to the one before it:

  • ids — the diaObjectId only, as an integer and as the string diaObjectId_str.
  • position — adds the object's ra / dec.
  • matches — adds a summary per match (catalog, source id, separation).
  • full — adds the complete published payload for each match.

Error — invalid parameter (400)

An unparseable timestamp, unknown detail/time_field, non-positive page_size, malformed or conflicting cursor, or an out-of-range window returns a 400 with a structured JSON error body. Branch on code; error keeps the original text and equals message:

{% verbatim %} 
{
  "error": "detail must be one of ('ids', 'position', 'matches', 'full'), got 'everything'",
  "code": "invalid_parameter",
  "message": "detail must be one of ('ids', 'position', 'matches', 'full'), got 'everything'",
  "param": "detail",
  "retryable": false
}
{% endverbatim %}

The same body shape carries unsupported_parameter (a filter or response parameter) and query_too_expensive (over the request budget), both 400 and not retryable.

Error — wrong method (405)

Only GET is supported. Any other method returns a 405:

{% verbatim %} 
{
  "error": "method not allowed",
  "code": "method_not_allowed",
  "message": "method not allowed",
  "retryable": false
}
{% endverbatim %}

Error — service unavailable (503)

When the service database cannot be reached, the response is a 503 with a Retry-After header; retry after that many seconds:

{
  "error": "The service database is temporarily unavailable; retry later.",
  "code": "service_unavailable",
  "message": "The service database is temporarily unavailable; retry later.",
  "retryable": true
